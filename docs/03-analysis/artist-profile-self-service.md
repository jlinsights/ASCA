# 본인 작가 프로필 저장

2026-10-24. Supabase Auth 전환 브랜치의 구현 기록이며 운영 배포 기록이 아니다.
기준 main은 `c6e35339`로 PR #121 문서·#122 LICENSE를 포함한다.

## 계정–작가 연결 계약

`artists.claimed_by_user_id`에는 **`auth.users.id`의 UUID 문자열**을 저장한다.
즉 `claimed_by_user_id = account.id`이며 컬럼 타입은 기존 `text`를 유지한다.
`artists.id`는 별도의 작가 UUID다. Clerk 사용자 ID나 이메일을 넣지 않는다.

`get_my_artist_ids()`가 `account_profiles.id::text`와 이 컬럼을 비교해
`account.artistIds`를 만든다. 계정 가입이나 프로필 저장은 작가 연결을 생성하지
않는다. 운영 작가 연결 관리 화면은 후속 Claude 작업이며 이 브랜치에 자동 연결을
추가하지 않았다. 연결된 작가가 없는 계정에는 편집 폼 대신 안내를 표시한다.

## 서버 API

`GET /api/profile/artists/[id]`와 `PATCH /api/profile/artists/[id]`를 사용한다.

- `getAccount()`로 검증된 native 계정을 확인한다.
- `account.artistIds.includes(id)`를 필수로 검사한다. 관리자도 본인 편집 경로의
  소유권 검사를 우회하지 않는다.
- 서비스 역할 쿼리에도 `id`와 `claimed_by_user_id = account.id` 조건을 함께
  넣는다. 조회 후 연결이 해제된 경우에도 과거 소유권으로 수정하지 못한다.
- PATCH는 PR #120의 `checkOrigin()`과 계정별 요청 제한을 유지한다.
- 비공개로 된 본인 작가는 편집할 수 있다. 서비스 역할을 사용하는 GET은 이 인증된
  본인 편집 경로에만 한정한다. 공개 작가 조회의 RLS는 유지한다.
- 응답은 필요한 필드만 명시적으로 구성하고 `private, no-store`로 반환한다. 회비
  상태·소유 계정·회원 등급을 응답에 포함하지 않는다.

공식 이름 `name`은 협회 관리 항목이므로 읽기 전용이며 PATCH에서 거부한다. 허용된
PATCH 필드와 실제 DB 열은 다음과 같다. 다른 키가 섞이면 요청 전체를 거부하며
조용히 무시하지 않는다.

| 요청 키          | DB 열         |
| ---------------- | ------------- |
| `nameEn`         | `name_en`     |
| `bio`            | `bio`         |
| `bioEn`          | `bio_en`      |
| `birthYear`      | `birth_year`  |
| `specialization` | `specialties` |

`updated_at`은 서버가 기록하며 클라이언트 입력으로 받지 않는다. 선택 필드의
`null`은 값을 지운다. 타입·문자 수·연도·배열 길이도 서버에서 검사한다.

`name`, `membership_type`, `visibility`, `dues_status`, `claimed_by_user_id` 및
이들의 camelCase 별칭을 받을 수 없다. `isPublic`도 수정할 수 없다. 공개 상태는
DB 트리거 결과를 읽기 전용으로 표시한다. 별도 자율 비공개 설정은 추가하지
않았다.

## 편집 화면과 기존 API

`fetchArtistProfile`·`updateArtistProfile`은 같은 출처의 서버 API를 호출하며
브라우저 Supabase 클라이언트로 작가를 직접 수정하지 않는다. 숨겨진 본인 프로필도
서버 GET에서 정확한 camelCase 모델로 읽어 기존 영문 소개 등이 누락되지 않는다.

실제 운영 스키마에 없는 연락처·지역·활동 연수·소셜 링크·공개 토글을 폼 저장
대상에서 제거했다. 기존 사진은 표시하지만 이 작업에서 새로운 사진 업로드나
포트폴리오 설정 저장을 구현하지 않았다. 미사용 레거시 직접 쓰기 함수도 제거해
없는 열을 저장하거나 실패한 업로드를 성공으로 표시하는 경로를 남기지 않았다.
필드는 소개·기본 정보에 한정하고 UI 문구는 한국어·영어·일본어·번체로 제공한다.

계정·작가가 바뀌거나 컴포넌트가 해제되면 이전 조회·저장 응답을 무시한다. 저장
전에 로드한 프로필 ID와 현재 작가 ID도 비교한다. 실패한 조회에서는 빈 저장 폼을
표시하지 않고, 실패한 저장에서는 성공 안내를 표시하지 않는다.

기존 `auditTrail.trackDataChange()`에 Supabase 계정 UUID·작가 UUID·변경 열
목록을 전달한다. 소개·출생연도 등의 원문을 감사 기록에 복사하지 않는다. 기존
감사 모듈은 프로세스 메모리 기반이며, 이 변경이 영구 DB 감사 저장을 구현한 것은
아니다.

## 검증

API 테스트는 익명·타인·미연결 관리자 거부, Origin, snake_case 매핑, 보호 열과
지원하지 않는 열 거부, 연결 해제 조건, 비공개 응답, 안전한 오류 처리를 검사한다.
화면 테스트는 작가 UUID 사용, 영문 필드 로딩, 연도 지우기, 실패 표시, 계정 변경
중 늦은 저장 응답 차단을 검사한다. 독립 코드·보안 리뷰의 응답 경합과 감사 기록
지적을 회귀 테스트와 함께 반영했다.

격리된 로컬 Supabase와 실행 중인 로컬 앱에서는 다음 명령으로 실제 계정·DB·HTTP
경계를 검사한다. 상태 파일은 비공개이며 토큰·키를 Git이나 출력에 남기지 않는다.

```bash
AUTH_LOCAL_STATUS_FILE=/private/tmp/asca-auth-local-status.json npm run test:profile-service
```

허용 주소는 별도 로컬 스택의 API `127.0.0.1:56321`, DB `127.0.0.1:56322`, 앱
`http://localhost:3105`다. `test:auth-service`가 준비한 최소 로컬 스키마를
사용한다. 테스트는 실제 저장 후 등급·회비·공개 상태·소유 계정 보존과 연결 해제
즉시 접근 거부를 확인하고, 만든 가짜 계정과 작가는 종료 시 삭제한다. 운영
데이터·계정·연결을 생성하거나 변경하지 않는다.

gstack `/browse`로 실제 로컬 계정의 로그인 → 비공개 작가 편집 → 영문 이름·소개
저장 → 새로고침 후 값 유지를 확인했다. 공개 토글이 없고 응답에 회비·소유권
정보가 포함되지 않는 것도 확인했다. 연결 해제 시 편집 상태에서 미연결 안내로
전환하는 회귀 테스트도 통과했다. 화면 확인은 운영 인증 렌더링 증거가 아니다.
