# Supabase Auth 화면·세션 전환

2026-10-24. `feat/supabase-auth`의 로컬 구현 기록이다. 운영 배포·운영 DB 변경·
기존 계정 이전·실제 인증메일 발송을 수행한 기록이 아니다.

후속 운영 DB 적용 상태는 [전환 준비 기록](supabase-auth-cutover-readiness.md)을
확인한다.

## 구현한 흐름

- Clerk 위젯·provider·런타임 SDK 호출을 Supabase SSR 기반
  로그인·가입·로그아웃으로 교체했다.
- 기존 Ink System 셸을 보존하고 입력란·상태·오류·약관 동의를
  한국어·영어·일본어·번체 중국어로 제공한다.
- 가입 계정은 기존 작가를 자동으로 소유하거나 협회 회원 자격을 획득하지 않는다.
- `/auth/callback`이 PKCE code를 교환하고 cookie를 기록한다. 복귀 주소는 내부
  경로만 허용한다. 만료·중복 사용·거부된 링크는 코드나 공급자 오류를 URL에
  노출하지 않고 다시 요청하도록 안내한다.
- `/forgot-password`, `/reset-password`에서 복구 메일 요청과 새 비밀번호 설정을
  제공한다. MFA 등록 계정은 비밀번호 변경 전에
  `/auth/mfa?next=/reset-password`에서 인증한다.
- `/auth/mfa`에서 TOTP 등록 QR/키와 일회용 코드 인증을 제공한다. 실제 SDK가
  돌려주는 QR data URI를 그대로 이미지로 표시한다.
- Proxy가 JWT 사용자를 검증하고 갱신·삭제된 cookie를 다음 요청과 응답/redirect
  양쪽에 보존한다. 인증 응답은 `private, no-store`로 처리하고 Origin 검증을
  유지한다. Playwright 환경변수로 인증을 우회하지 않는다. 운영 환경에서는
  브라우저·서버·proxy의 인증 cookie에 `Secure`를 설정한다.
- `/api/auth/session`에서 현재 DB 프로필·정지 여부·검증된 MFA 수준·연결된 작가
  UUID를 조회한다. 클라이언트의 오래된 조회 결과가 새 로그아웃 상태를 덮어쓰지
  않도록 요청 순서를 확인한다.
- 관리자 layout과 공통 API 경계는 DB 역할과 `aal2`를 모두 요구한다. 회원 API의
  관리자 예외에도 MFA 조건을 명시하고, 본인 계정으로 회비 등급/승인 상태를
  변경하지 못하도록 막았다.
- 아카이브 작성자는 이메일 allowlist 대신 검증된 DB 계정을 사용한다. 실제
  Storage 업로드와 소유권 검증을 제공하는 `/archive/submit`로 이전 작품 업로드
  경로를 연결했다.
- 계정 UUID를 작가 UUID로 사용하던 화면의 조회를 연결된 작가 ID로 바꿨다. 신규
  `/profile`은 계정 이름 수정과 작가 미연결 안내, 아카이브/MFA 진입점을
  제공한다.
- 레거시 GraphQL의 작가·작품 직접 쓰기는 관리자에게만 허용한다. 소유자 없는
  레코드를 일반 계정이 수정하던 조건을 제거했다. 작가는 검증된 아카이브 제출
  API를 사용한다.
- 기존 Clerk webhook 쓰기는 410으로 종료한다. 외부 Clerk 설정·계정과 롤백용
  의존성은 삭제하지 않았다.
- 인증 화면에서 상담 플로팅 버튼이 약관 문구를 가리는 현상을 확인하여 인증
  경로의 위젯 렌더링을 제한했다.

## 검증과 한계

타입검사, lint, 전체 Jest 테스트, 인증/MFA/callback/cookie/권한 회귀 테스트와
`NODE_ENV=production npm run build:full`이 통과했다. lint에는 기존 파일의 줄 수
경고만 남아 있다. 변경 파일 포맷과 AGENTS/CLAUDE 본문 일치도 확인했다. 인증 관련
테스트를 기존 제외 목록에 추가하거나 테스트 기준을 낮추지 않았다.

gstack `/codex` 독립 리뷰에서 확인한 회원 API MFA 우회, MFA 복구 경로, QR data
URI 이중 인코딩 결함을 회귀 테스트와 함께 수정했다.

gstack `/browse`로 로컬 프로덕션 빌드의 로그인·가입·복구 화면, 입력 필드·약관,
모바일 가로 넘침, 익명 관리자 접근 시 로그인 이동을 확인했다. 이는 화면·분기
검증이다. 로컬 placeholder URL/키를 사용한 빌드는 실제 Supabase 인증 연결 증거가
아니다.

당시 Docker 데몬 미실행으로 남았던 실제 GoTrue·메일·MFA 검증은 후속 단계에서
수행했다. 최신 main 통합과 실제 서비스·브라우저 증거, 운영 설정 확인 범위는
[전환 준비 기록](supabase-auth-cutover-readiness.md)을 확인한다. 기존 1단계 RLS
검증은 별도 PostgreSQL에서 수행했다.

현행 ASCA-2026에 없는 레거시 회원 테이블을 이 작업에서 생성하지 않았다.
`/api/members/me`는 가짜 회원을 만들지 않고 미구축 상태를 404로 반환한다. 기존
회원/공모전/전시의 직접 CMS 쓰기는 기존 RLS 제약을 유지하며, 이 작업을 해당 제품
기능의 완성으로 해석하지 않는다. 검증된 작가 작품 제출은 아카이브 API를
사용한다.

## 운영 전환 전 필요한 순서

1. 최신 main `f1099fba`의 PR #117·#118을 통합했다. 다른 작업 트리의 변경과
   복구용 stash를 보존했다. 후속 변경이 생기면 다시 비교한다.
2. 실제 프로젝트 `caxjyimsuvjnbmjoxfad`의 백업/복원 가능 상태를 확인한다. 검토한
   `20261024142344_supabase_auth_foundation.sql`만 적용한다. 과거 마이그레이션
   재실행, 전체 Drizzle 스키마 push, 초기화는 하지 않는다.
3. Preview/운영의 Supabase URL·공개 키·서버 키·DATABASE_URL이 같은 프로젝트를
   가리키는지 확인한다.
4. SMTP 서비스와 검증된 발신 주소를 설정한다. 기본 이메일 발송은 운영용으로
   사용하지 않는다. UI의 비밀번호 길이 제한과 별도로 Supabase Auth 서버의 최소
   길이·정책을 일치시킨다. 이메일 인증 필수, Site URL, `/auth/callback` redirect
   allowlist와 rate limit을 점검한다.
5. 기존 Clerk 사용자의 신원을 확인하고 `auth_identity_links`로 신규 UUID를
   연결한다. 비밀번호/세션 자동 승계를 전제하지 않고, 검증되지 않은 이메일
   일치로 계정을 합치지 않는다.
6. 승인한 관리자 역할·기존 작가 소유권을 개별 연결하고 기록한다. 테스트 때문에
   일반 계정에 권한을 임의 부여하지 않는다.
7. Preview에서 실제 가입·인증메일·로그인·복구·로그아웃·MFA·작품 제출과 타인 수정
   차단을 확인한다.
8. 운영 전환 후 실제 인증 렌더링과 로그를 확인한다. Clerk 설정·계정은 롤백 기간
   동안 보존한다.

이번 단계에서는 실제 사용자에게 초대·인증메일을 발송하거나 운영 제공자를
변경하지 않았다.
